# Design

以可证伪的 owner 承诺为准，审计当前测试的独立证明价值，而非追求删测数量或时长收益。

## Context

[测试策略](../../docs/testing/strategy.md)要求测试有当前 owner 与可观察结果；[Case](../../docs/testing/case-maintenance.md)连接证据，但映射闭合不证明断言正确。用户已澄清要求全量普查：之前只审 138 个实体不能视为本 Change 完成。实际删除与重写留给普查后的独立实施。

## Goals / Non-Goals

目标是完整审读当前全部测试，给出可核对的清理候选、保留依据和实施顺序。不按数量配额删测，不重构被测实现，不降低验收、不放宽预算，也不把一次性能失败归因为测试质量问题。

## Decisions

### Intended Change

- Gate、package、Markdown link 的既有审计在输入未变的前提下继续有效；其余按 repository、package tools、analyzers、Run outputs、scheduler、Run/Definition、data/JSON/command、scanners/scope 八个互斥完整分区并行审读。
- 每个子代理读取其分区全部实体正文、矩阵和实际委托材料，写入独立报告；正式源码与 Case 只读。局部工具缺索引时用明确路径继续读，不将未读项当作不存在。
- 从 owner → 可观察故障 → 测试断言 → 独立性/可靠性/维护价值判断。允许同一契约在不同边界各有直接证据。
- 候选必须说明具体缺陷、保留/替代证据和最小动作；测试体有缺陷但独占义务时归为改写，不直接删除。
- 以官方 Case 查询和全树 registration 闭合恢复完整当前清单；分区和已审 keys 仅保存在 Git 忽略的本地证据中，最终核对并集与哈希，确认未遗漏或漂移。不另建提交实体账本。

### Resulting Impacts

- 主代理复核跨层重复候选与最优先清理项，筛掉仅风格偏好或性能推断。
- 审计文档保留形成时依据，不成为产品/测试策略的新规范；明确声明的非日常入口和委托验收单列核对，不能用常规 766 的计数掩盖它们。
- 验证以现有全树闭合及文档材料检查为主；只读审计不重跑完整 Gate，不以旧性能失败宣称本轮验证失败。

## Risks / Trade-offs

静态审查不能完全证明测试的缺陷检测能力。证据不足时标记待验证，不能宣称已证明安全删除。邻近 mock/fixture 相似不意味着真实入口、故障层或契约相同。

## Open Questions

无范围阻塞；全量普查完成后再决定具体候选的清理动作。
