# Proposal

本 Draft 评估声明式派生 flag 的增量价值；当前优先使用手动声明，保留低优先级的重新评估入口。

## Why

现有 flag DSL 已支持把组合条件命名并复用。声明式派生 flag 则会在条件成立时产生新的运行时 token，
让其它条件和回调消费同一语义结果，可能改善集中声明与读取体验。

目前没有已确认的急切需求。语义命名、隐藏组合细节和跨 Check 复用可由常量、共享声明或 helper 完成；
调用方已知的普通 flags 也可在调用前手动组合成新 token。这些场景下，内置机制主要改善体验，而非填补能力缺口。

## Outcome

保存暂不实现的判断及其适用边界。后续以真实消费者场景比较手动方案和内置派生的收益、成本，再决定是否进入 Plan。

命名条件的用户指导由独立的 `document-reusable-flag-conditions` Change 承接；用法可发现性与派生机制评估分别推进。
