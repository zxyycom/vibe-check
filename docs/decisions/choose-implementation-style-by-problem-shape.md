## 目的
- 让实现者和 reviewer 能从问题形态恢复优先实现模型，并用共同边界判断局部表达是否仍然
  清楚、可验证且符合组件责任。

## 背景
- 现有编码规范已经覆盖规则 owner、运行边界、类型、错误、模块和验证，但同一职责仍可由
  多种控制流、状态管理和抽象风格表达；其中一些写法会隐藏顺序、不变量、失败或副作用。
- 仅依靠 lint、相邻源码或函数长度不能判断实现模型是否贴合问题，也不能阻止为了模式、
  复用或语法简短而增加不必要抽象。

## 决策
- 采用: `docs/coding-style.md` 作为实现风格的唯一 owner，按主导问题形态给出优先实现模型和
  必须呈现的价值，并为控制流、条件、集合处理、mutation、异步、函数参数、命名、注释和
  抽象建立可审查的局部表达边界。
- 采用: 同一职责保持稳定表达；只有更具体的行为 owner、公共兼容性、经过测量的性能约束或
  现有组件契约可以支持偏离，且理由与验证证据必须在受影响实现附近可恢复。
- 采用: 风格约束不使用固定文件或函数长度、强制设计模式、预设共享层或特定第三方依赖代替
  工程判断；没有相应问题信号时选择能够完整表达当前职责的最小实现。
