## 目的

- 让 Core、内部消费者与随包工具共同依赖文件—区域关系，保留来源获取与领域策略的清楚边界。
- 支持多份来源的组合和追加，以双向定位为核心，按实际需要确定扩展能力。

## 背景

- 内部区域文件集合与多个 Check 的反向索引具有共同成员语义；阈值和领域 policy 则由各消费者解释。
- 追加的实际需要是接入更多文件源或区域源。合并已有数据后重建关系即可作为初始路径，
  尚无证据要求实时成员维护或复杂的局部增量算法。
- 文件获取按[收集决策](unify-file-selection-with-default-excludes.md)独立演进。
  关系计算归公共 Core，直接消费调用方提供的值数据，不依赖文件获取的生命周期。

## 决策

- 采用: **共同输入与双向定位。** 来源 owner 提供多份文件路径及区域值数据，支持批量接入和显式追加，
  形成一个只读关系视图；从文件定位全部所属区域，从区域定位全部成员文件，保留零命中与多重成员。
- 采用: **合并与身份。** 各来源使用共同路径坐标和区域身份，文件合并去重，区域 ID 冲突明确校验，
  不静默覆盖。区域规则复用 Product 生效的共同 matcher；已知实际成员直接建立关系，保持来源筛选结果。
- 采用: **追加生命周期。** 先合并已接收的数据，再重建双向关系并取得新视图，旧视图保持不变。
  构造、查询及重建均无 I/O，不重新获取旧来源；输入刷新由来源 owner 显式负责。
  该路径保持调用内状态，不增加实时更新或跨调用隐藏缓存。
- 采用: **责任与只读边界。** 扫描、剪枝、默认排除、Git 事实和新鲜度归来源 owner；
  Check eligibility、accepted/rejected、阈值、领域 policy 与结算归消费者。
  索引保留显式输入，包括不存在或已删除路径；封闭修改通道，内部存储保持私有。
- 采用: **扩展与工程收敛。** 双向定位是核心职责而非接口数量上限。名称、类型、输入组合校验、
  未知键约定和存储由工程确定，不增加路径域策略开关或来源获取框架，也不预先承诺性能收益。
  临时输入可复用纯计算构造独立结果，无需登记到既有视图；本方向不要求独立公共试算 API 或新增机制作为交付项。
