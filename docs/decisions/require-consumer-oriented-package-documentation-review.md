## 目的

- 让包使用者仅凭实际可获得的页面、公开声明说明和示例完成集成与深入使用。
- 将对外文档质量审查设为可独立开展、每次发布必需执行的职责。

## 背景

- [文档影响审查](review-documentation-impact-by-audience.md)从行为 diff 反查同步责任；材料、投影、链接、类型和示例验收证明各自的可执行事实。两者均未覆盖说明本身的完整质量判断，未修改页面、入口缺口和过密组织仍可能妨碍使用。
- 内容审查也适用于发布之外的专项维护，方法应由文档 owner 拥有。[固定发布流程](standardize-package-release-procedure.md)已有同包验收与 evidence 位置，可承接发布触发和结论保存。

## 决策

- 采用: 由[文档 owner](../tooling/documentation.md#对外文档使用者审查)完整定义独立的包消费者审查，覆盖实际包中的用户文档、示例、公开声明及必要字段和辅助类型 JSDoc。正式发布覆盖全集，包括未修改内容；专项审查可限定范围，结论仅适用于该范围。
- 采用: 非实施代理先从使用者阅读路径判断用途、完整性、准确性、一致性和可读性，再用行为证据核验。内部知识不能补齐用户拿不到的说明；精简表达时保留重要安全边界和必要规格。
- 采用: [发布 owner](../tooling/package-release.md#发布前对外文档复核)负责每次触发、正式包身份确认和放行。准备期尽早修正，发布前取得适用于最终 tarball 的独立结论；覆盖不足、必要核对或独立结论缺失、影响正确使用的问题未解决时阻断发布。
- 采用: 包身份、覆盖、代表性任务、审查者、发现与处理保存在已有任务/Change 中，发布复用 release evidence 与归档。材料或相关行为变化后复核，正式输入修正遵守重新冻结和同包完整验收。
- 采用: 日常 diff 影响审查、机械验收和内容语义审查各自提供证据，检查成功或清单勾选不能代替内容判断。语义要求由执行者落实，沿用已有记录，不新增产品行为、CLI 审批字段或平行账本。
