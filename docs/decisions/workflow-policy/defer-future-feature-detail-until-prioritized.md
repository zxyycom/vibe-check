## 目的
- 让未来功能材料清楚表达要解决的问题和不可跨越的边界，而不把尚无实现证据的设计猜测误当成长期契约。
- 让字段、接口、算法、状态、失败处理和测试证明在真实依赖稳定且功能即将实施时一次收敛。

## 背景
- 当前多个 Markdown、JSON、路径、秘密与网络检查 change 只代表未来方向，从未进入实现。
- Check、Record、任务编排与项目定义等基础边界仍在演进，过早固定 feature 级 schema、状态机、缓存和验收矩阵已经产生大量随基础变化失效的细节。
- 结构完整但高度推测的 change 容易被后续 agent 误读为已确认且可直接实现的方案，增加维护和返工成本。

## 决策
- 采用: 未排期或尚未准备实施的 feature change 只维护产品结果、范围与非目标、关键安全或兼容边界、责任 owner、前置依赖和高层验收方向。
- 采用: 这类 change 不提前冻结精确 public fields、schema shape、CLI 细节、算法、状态机、缓存键、并发策略或完整测试矩阵；基础架构变化时主动删除已经失去依据的推测性细节，不为从未实施的 artifact 保留兼容层。
- 采用: 某项功能进入实现准备后，必须先依据届时的主规范、运行时代码、活动决策和已落地基础 change 重新基线，再补齐可唯一实施的 proposal、design、delta specs 与 tasks，并完成阻塞级审计后才能实施。
- 采用: 正在建立且明确作为近期实现前置的基础 change 不适用上述粗化豁免，仍需把其自身公共契约、失败边界和验收写到可实现、可验证的程度。
