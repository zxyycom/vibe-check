# 编码规范

本文档是 Vibe Check 实现者和 reviewer 的通用实现质量 owner，同时拥有项目自有 package 对外说明的
语言规则。它与具体行为 owner、目标代码、相邻类型和测试一起使用，约束工程判断、实现模型、局部
表达、边界处理、职责分层和交付验收；修改 package 对外说明时，它还规定中文主叙述的范围、判断和例外。
产品行为契约、当前架构以及 package documentation 的生成与验证机械流程继续由各自 owner 定义。

使用本文的预期结果是：代码直接呈现 owner、领域含义、主要数据流、状态与失败、模块关系和
验证证据；对外说明以中文直接呈现 consumer 所需的用途、正确使用方式和边界。实现者能按问题
形态选择最小实现，reviewer 能区分阻断性违规、审查信号和无需统一的风格差异，并只要求影响相称的整改与验证。

## 1. 使用顺序与裁决

### 1.1 读取顺序与内容 owner

按以下顺序使用本文：

1. 从[文档导航](navigation.md)选择目标的行为或流程 owner，确认稳定契约、编辑归属和受影响边界。
2. 修改实现代码时，读取目标代码、相邻类型和测试，恢复当前调用与集成事实；修改 package 对外说明时，读取本节 6.4 与[脚本工具](script-tooling.md#documentation-validation-and-package-material)。
3. 对实现代码使用本文选择实现模型、检查局部表达并确定验证层级；对 package 对外说明使用 6.4 判断适用范围、中文主叙述和例外。
4. 运行与改动相称的行为或文档验证入口；TypeScript、Oxlint 和 Oxfmt 继续只覆盖适用的实现改动。

行为 owner 拥有具体命令行为、输出字段、schema、指标和测试语义；本文拥有实现这些契约时的
通用代码质量，以及项目自有 package 对外说明的语言规则。项目工具配置与脚本 owner 拥有可机械
执行的 lint、format、文档投影和验证，当前入口见[脚本工具](script-tooling.md)。行为 owner 与本文发生
直接冲突时，行为 owner 优先；没有直接冲突的通用质量要求仍然适用。

相邻代码只提供当前接口和调用事实，不得覆盖行为 owner、本文或工具配置。既有实现即使偏离
本文，也不构成新增或修改代码继续偏离的依据。

### 1.2 规则强度

| 标记 | 含义 | 交付影响 |
| --- | --- | --- |
| **必须 / 不得** | 阻断性要求 | 不满足且没有有效例外时，改动不能验收 |
| **应 / 优先 / 默认** | 推荐路径 | 可以采用其他表达，但仍必须满足阻断性要求并呈现相同语义价值 |
| **审查触发信号** | 需要核对的风险信号 | 只触发继续审查，不单独证明违规或指定重构方案 |

更具体的行为 owner、公共兼容性、经过测量的性能约束或现有组件契约可以形成阻断性要求的
例外。例外必须指出适用规则和影响范围，理由必须能从相邻代码、测试或 owner 恢复。个人偏好、
附近代码、“AI 或人最终仍能推断”以及单个语法、分支数量、嵌套深度、函数长度或复杂度数值
都不是例外依据。

### 1.3 审查结论

审查使用以下三种结论，不要求为每个函数填写表单；没有具体问题或例外时，“符合”可以保持
隐式，不需要独立记录：

- **符合：** 没有阻断性违规；审查信号未形成具体语义障碍时，无需风格整改或独立记录。
- **例外：** 说明被偏离的阻断性要求、依据、适用范围和相邻证据；例外只覆盖该冲突。
- **必须整改：** 指出被遮蔽的职责、条件、状态、顺序、失败或副作用，以及需要恢复的最小语义
  边界；不能只报告行数、分支数或“难读”。

验收标准：实现者和 reviewer 能从实际文本得到同一规则强度、适用范围、例外依据和交付结论。

## 2. Owner 与实现归属先行

实现代码必须服从主规范定义的职责边界和稳定契约。owner 是规则来源文档；实现归属是承载代码的 source area、模块、文件或脚本。

新增逻辑应先进入最明确的现有实现归属。只有职责、变化原因、复用边界或命名空间清晰时，才新增模块、package 或共享层。

优先在稳定 owner 中完成可维护实现。确需临时处理时，必须在相邻代码或 TODO 中写明适用范围和
移除条件；不得为短期跑通建立难以移除的第二套长期实现。

跨实现归属协作必须通过显式类型、稳定输出或主规范定义的边界完成。调用入口必须只处理本入口负责的解析、校验、归一化和映射；属于下游组件的 opaque 值或业务语义原样传递。

共享代码必须承接多个实现归属共同依赖的不变量、错误映射或数据结构，并具有清晰命名和验证
入口；满足这些条件后才抽出公共模块。

验收标准：新增或修改的代码能回答“谁定义规则、谁实现规则、谁消费结果、谁负责失败反馈”。

## 3. 边界代码显式

用户输入、脚本命令参数、配置、路径、文件系统、进程、JSON、schema 和 scanner 输出都属于边界。边界代码负责解析、校验、归一化和错误映射；内部逻辑必须只处理已经归一化的领域对象。

边界失败必须给调用方明确反馈：

1. 脚本命令返回稳定退出码、清晰错误或可行动诊断。
2. 验证脚本说明文件、字段、命令和原因。
3. 机器输出、stderr/stdout 和人读报告保持各自通道职责。

不得用空结果、猜测默认值、静默跳过或隐式降级掩盖失败。可恢复兜底必须能追溯到主规范定义的输出层规则，并保留足够定位依据。

验收标准：任何失败路径都能回答“调用方下一步该看什么、改什么或重试什么”。

## 4. 类型表达领域含义

跨模块传递领域含义时，优先使用能表达不变量的 TypeScript 类型、discriminated union 和
只读数据结构。裸字符串、通用 JSON 值和 tuple 只适合协议镜像、opaque options、错误
details、测试构造和局部 glue code；外部输入先以 `unknown` 接收并在边界完成校验，不用
`any` 绕过边界。

类型设计必须遵循三条原则：

1. 业务逻辑入口接收已经校验过的领域值，不重复解析原始输入。
2. 稳定序列化类型保持字段形状清晰，不把私有语义塞进共享输出。
3. 公开 API 通过返回值、显式 result union 或可识别的 error 表达普通失败，不把缺失工具、解析失败或非法输入伪装成成功空结果。

稳定字段、错误码、退出码、schema 名、诊断前缀和跨函数复用的字符串或数字，应使用枚举、新类型、常量模块或职责内配置表达。不得建立跨组件的全局杂物常量池。

验收标准：阅读函数签名时，可以区分“原始输入”“领域对象”“输出模型”和“私有参数”。

## 5. 按问题形态选择实现模型

按以下顺序选择实现模型：

1. 行为 owner 或组件契约已经规定模型时，使用该模型。
2. 没有更具体约定时，识别当前职责的主导问题形态。
3. 从下表选择能直接呈现不变量、数据流和失败路径的模型。
4. 只有模型需要且触发条件成立时，才使用预置能力。
5. 用测试或等价证据验证表中声明的实现价值。

一个流程可以在明确的职责边界内组合多种模型，但同一职责应保持稳定表达。

| 主导问题形态 | 优先实现模型 | 实现必须呈现的价值 |
| --- | --- | --- |
| 无状态计算或数据转换 | 纯函数与显式组合 | 输入输出直接，计算可独立验证，不依赖隐藏状态 |
| 有明确顺序、副作用和失败恢复的工作流 | 结构化过程或事务式流程 | 执行顺序、提交点和失败路径连续可见 |
| 有稳定身份、生命周期或持续不变量 | 对象或 class 封装 | 状态和行为由同一责任边界维护，非法状态不向外泄漏 |
| 取值与分支集合封闭，结果只取决于当前值 | 判别联合与穷尽分支 | 合法取值和处理完整显式，新增分支能够被整体检查 |
| 行为同时取决于当前状态和事件，合法转移受约束 | 显式状态转移模型 | 状态、事件、guard 和合法转移能够分别识别 |
| 调用契约稳定，但行为需要独立替换或扩展 | 接口、策略对象或多态 | 差异集中在实现侧，调用方不重复选择规则 |
| 存在大量同构规则、字段或映射 | Schema、表驱动或声明式定义 | 规则集中且结构一致，扩展主要修改定义而非复制控制流 |
| 数据经过多个职责稳定的连续阶段 | 流水线 | 阶段输入输出和组合顺序清楚，各阶段可单独验证 |
| 独立参与方围绕事件和时序协作 | 事件或消息驱动 | 事件契约、订阅者责任和时序影响显式 |
| 数据关系、访问模式或批处理成本主导实现 | 数据导向设计 | 数据布局贴合真实工作负载，复杂度取舍有测量依据 |

预置能力只解决下表列出的语义，不构成迁移要求：

| 能力 | 使用条件 | 使用边界 |
| --- | --- | --- |
| `TypeBox` | 行为 owner 需要 runtime Schema、外部数据解析和静态类型派生 | 复用已有 Schema owner，不建立同义 Schema |
| `neverthrow` | 可预期失败需要跨多个步骤或异步流程组合 | 简单局部边界继续使用已有 typed error 或显式 result union；同一边界只使用一种失败协议 |
| `ts-pattern` | 封闭分支包含非平凡的判别联合、嵌套结构或表达式结果，并需要穷尽检查 | 简单单值分支使用原生 `switch` 与 `never`；它不承接状态机生命周期 |
| `Remeda` | 连续无状态数据转换是当前职责的主要结构 | 简单数组操作使用原生方法；复杂分支、副作用或 `await` 使用结构化循环 |
| `Mnemonist` | 访问模式、复杂度或专用语义明确需要 Heap、Deque、Trie、LRU 等结构 | 普通集合使用原生 `Array`、`Map` 与 `Set` |

选型依据与复核边界见
[Result/Option](investigations/implementation-libraries/result-and-option-libraries.md)、
[穷尽匹配/状态建模](investigations/implementation-libraries/pattern-matching-and-state-modeling-libraries.md)
和[函数式工具/数据结构](investigations/implementation-libraries/functional-utilities-and-data-structures.md)
调查。没有表中触发条件时，使用能完整表达当前职责的最简单语言结构。现有能力不能覆盖真实
问题时，把缺口交给依赖 owner 重新评估；实现任务不临时安装同类替代库，也不建立第二套基础原语。

验收标准：实现者能说明主导问题形态、所选模型及其兑现的价值；reviewer 无需从语法偏好猜测
状态、顺序、扩展点或失败语义。

## 6. 局部表达保持可推理

代码是后续实现者和 reviewer 的主要语义输入。能够通过遍历完整调用图、测试或额外推断还原
含义，不代表局部表达已经合格。新增或修改代码必须直接呈现当前职责需要理解的主要数据流、
领域条件、状态变化和失败路径。

### 6.1 阻断性语义下限

1. 决定主要结果的复合条件必须能从局部表达直接恢复，必要时由领域名称承接；mutation 和副作用
   必须有可识别的 owner、发生位置和观察方式。
2. 多个取值共同表示一个领域状态且存在无效组合时，必须由类型、构造边界或集中校验排除无效
   状态，并由一个连续责任边界维护该不变量。
3. 解析、领域判断、副作用、输出或错误映射可以在小型入口中连续组合；开始相互交错并遮蔽执行
   顺序、提交点或失败归属时，必须用领域名称、具名阶段或职责拆分恢复边界。
4. helper、wrapper、class、interface 或共享层必须拥有可命名结果、不变量、生命周期、变化原因或
   独立证明责任；只缩短代码或转发参数不能证明抽象成立。
5. 跨步骤或跨模块承载领域含义的名称必须区分其职责；`data`、`item`、`value`、`result` 或
   `handle` 只有在局部上下文已经给出单一含义时才能承载该职责。

### 6.2 默认表达与审查信号

| 关注点 | 默认表达 | 审查触发信号 |
| --- | --- | --- |
| 控制流 | 前置条件和失败使用 guard clause，主要成功路径保持连续 | 嵌套分支迫使读者同时记住多个条件，或提前返回把一个简单决策切碎 |
| 条件表达 | 三元表达式只用于一个清楚的二值选择；封闭集合使用穷尽分支 | 嵌套三元表达式；同一复合条件重复出现；条件同时决定多个互不相关的行为 |
| 集合处理 | 直接无状态转换使用 `map`、`filter`、`flatMap`；含 `await`、短路、分支副作用或有状态累计时使用结构化循环 | 用 `reduce` 隐藏多步工作流或可变累计器；用异步 `forEach` 制造未观察 Promise；长链中混入分支与副作用 |
| 状态与 mutation | 默认使用 `const` 和只读输入；局部 mutation 只在 owner、生命周期和提交点一眼可见时使用 | 修改调用方传入对象；跨模块共享可变状态；通过闭包或 module global 隐藏一次调用的状态 |
| 异步与并发 | 有依赖的步骤顺序 `await`；相互独立且规模有界的工作才并发；需要限流时使用已有调度边界 | 漂浮 Promise；为缩短耗时盲目 `Promise.all`；把本应独立的工作意外串行化；在循环中隐藏无界并发 |
| 函数与参数 | 函数围绕一个可命名结果；多个同类型或可选参数使用具名 options；helper 承接真实领域步骤或独立证明责任 | 用布尔 flag 切换互不相关流程；只转发参数的 wrapper；仅按行数拆函数；用位置参数迫使调用方记忆含义 |
| 命名 | 使用领域名词和明确动作或结果；布尔值使用 `is`、`has`、`can`、`should` 等可判读前缀；路径、单位和时间基准写入名称 | 在跨函数或跨模块契约中使用裸 `data`、`item`、`value`、`result`、`handle` 等无法区分责任的名称 |
| 注释 | 解释取舍、不变量、边界责任、非显然约束和必须保留的原因 | 复述语法或控制流；用注释代替可命名结构；没有适用范围和移除条件的长期 TODO |
| 抽象 | 选择直接兑现当前模型价值的最小结构；需要共享时围绕稳定不变量、owner 和消费方组织 | 把 class 当命名空间；为单一局部实现预设接口；因假设复用建立 generic helper；用新抽象包住已有抽象而不增加契约 |

链式表达只有在每一步仍能用领域语言识别时才保持内联；回调需要多层分支、mutation、错误映射
或副作用时，改用具名阶段或结构化循环。审查信号不自动要求改动；reviewer 必须把信号关联到
具体语义障碍，代码已经满足阻断性语义下限时可以保持原样。

### 6.3 最小整改与作用范围

需要整改时按以下顺序选择能恢复语义的最小动作：

1. 给条件、中间结果、状态或单位补充领域名称。
2. 分离领域决定与副作用，或让状态变化和失败归属连续可见。
3. 把共同维护一个不变量的取值集中为显式状态表达或具名阶段。
4. 只有形成独立职责、变化原因或稳定共享不变量时，才拆模块或建立抽象。

本节约束新增或修改代码及其直接受影响范围。邻近旧代码只有在它阻止本次改动满足阻断性语义
下限时才需要同步治理；局部修改不触发无关模块或全仓重构。偏离默认表达仍须满足阻断性要求；
“附近代码也这样写”本身不是偏离依据。

验收标准：reviewer 可以沿单一局部路径恢复输入如何成为结果、状态在哪里改变、异步工作何时
完成，以及每个抽象解决了什么当前问题。

### 6.4 package 对外说明以中文叙述为主

本节是项目拥有的 package 对外说明的稳定语言规则 owner。修改这类材料或审查其改动时使用本节；产品契约仍由行为 owner 定义，README/JSDoc 的生成与验证机械流程仍由[脚本工具](script-tooling.md#documentation-validation-and-package-material)拥有。

#### 适用范围

- package README template 及其生成的 root `README.md`。
- package entry 说明、public root JSDoc，以及 consumer 为正确使用 public API 必须读取的 supporting declaration 或字段 JSDoc。

#### 判断标准

- 说明以连续、可理解的中文叙述承载用途、正确使用方式和边界。reader 无需依赖另一段英文说明，即可从当前中文叙述恢复这些主要含义。
- “中文为主”是编辑判断，不按字符比例计算，也不要求逐字翻译或双语镜像。
- 现有 public-root JSDoc 中文检查只提供局部证据；它不是对全部对外材料的语言门禁，也不应被扩展为全面 gate。

#### 可保留原文与排除范围

- API identifier、代码与 code block、字面量、schema/协议字段、命令、路径、专有名、互操作材料和法律惯例材料可以保留原语言；需要时由周围中文说明其语义和边界。
- 内部实现注释、历史 provenance/归档材料、机器契约和其它不面向 package consumer 的文档不在本节的机械整改范围；只在各自 owner 或任务明确要求时修改。

#### 修改与验收路径

1. 修改 package guide 时编辑 README template；修改 declaration 说明时编辑 source JSDoc。不得直接把 generated README 或 generated JSDoc example 当作新的内容 owner。
2. 依照[脚本工具](script-tooling.md#documentation-validation-and-package-material)运行对应 projection 和验证；审查时确认范围内说明满足本节判断标准，且没有把该规则误实现为全量字符检测或无差别翻译。

验收标准：agent 或 reviewer 能从本节确定是否适用、中文主叙述的通过条件、可保留原文、排除范围以及正确编辑和验证入口。

## 7. 错误处理与结果模型

错误类型按边界和调用方需求设计。内部 helper 可以返回具体错误；跨模块和脚本命令边界应映射为稳定、可解释、可测试的错误模型。

错误处理规则：

1. 可预期失败使用显式 result union、受控 exception 或调用链已有的 typed error；不得混用多种失败协议描述同一边界。
2. Promise 必须被 `await`、返回或显式处理；生产路径不得遗留未观察 rejection。
3. 外部命令失败、工具不可用、解析失败和无发现分别建模。
4. `catch` 中把未知值按 `unknown` 处理，并在统一边界生成可定位、可行动的消息。

验收标准：错误路径能被测试或命令输出观察到，并且不会把不同失败混成同一种状态。

## 8. 目录、文件与模块命名

文件、模块和目录应围绕稳定 owner 与变化原因组织。编码规范不拥有当前项目的固定目录、入口
名称或依赖图；这些事实由当前[架构](architecture.md)、行为 owner 和
[脚本工具](script-tooling.md)定义。本节只规定布局与命名必须表达什么语义。

### 8.1 目录表达模块关系

实现源码中的目录是模块所有权边界，每一层都必须增加可识别的 owner 含义：

| 结构 | 必须表达的关系 |
| --- | --- |
| 文件直接位于某目录 | 该文件的职责由当前目录表示的模块直接拥有 |
| 子目录位于父目录 | 子目录是父模块拥有的下级模块 |
| 多个目录具有同一父目录 | 这些目录是同一 owner 下的同级模块 |

同级模块使用同一父目录，目录深度只表达 owner 的父子关系，不表达文件数量或实现规模。形成
独立 owner、变化原因、消费边界或内部职责集合时再建立子目录；文件类型、开发阶段或临时任务
本身不足以形成长期模块。

目录名使用 kebab-case，并且必须使用能够长期识别 owner 的领域名词或能力名称。单复数服从领域
含义。`current`、`common`、`shared`、`utils`、`helpers`、`tools`、`workflows`、`misc` 等通用词
只有在行为 owner 已赋予唯一、可验证的领域含义时才构成有效目录名；包装层和重复父目录名称也
必须提供新的 owner 含义。

目录边界表达模块所有权和层级关系。Public API、barrel、package、运行时隔离、跨模块可见性和
依赖方向需要各自的架构契约，不能只从目录存在推断。

### 8.2 文件名表达模块内职责

文件名必须与所在目录共同表达一个具体能力、动作、结果、边界或证明责任。目录已经提供模块
上下文时，文件名应补充模块内职责；公共身份、跨目录检索或歧义消除需要时可以保留必要重复词。

| 文件角色 | 命名要求 |
| --- | --- |
| 实现文件 | 职责 stem 使用 kebab-case；文件名、主要职责和主要导出能够相互对应 |
| 单文件配对测试 | 使用相同职责 stem 和测试工具规定的 role suffix |
| 跨文件行为测试 | 使用被证明的行为或契约名称 |
| 模块入口 | 使用具体行为或契约名称；`index`、`main`、`entry` 保留给外部工具或稳定消费契约要求的默认入口 |

`model`、`types`、`data`、`value`、`current`、`common`、`shared`、`utils`、`helpers`、`manager`、
`handler` 等通用词只有在目录上下文已经给出单一、可验证职责时才构成完整文件名。测试辅助、
声明和其他工具角色继续使用对应工具链规定的 suffix。

模块边界本身不要求 barrel。默认导入具体职责文件；只有 owner 定义了稳定聚合契约时，才建立
集中 export surface。

### 8.3 拆分、提升与移动

单个文件可以承载模块内的一项职责。该职责形成下级职责、独立消费边界或独立变化原因时，应提升
为子模块目录；现有子目录不再表达下级 owner 时，应合并或移动到正确层级。

以下情况触发拆分或层级审查，但不自动指定目标目录：

1. 同一文件同时承载多个组件职责、多个输出边界或多个边界类型。
2. 新功能需要反复修改无关代码。
3. 测试、fixture、解析、输出和错误映射互相遮蔽。
4. 多个同级文件持续使用同一职责前缀，并形成共同依赖或变化原因。
5. reviewer 无法用一句话说明目录或文件的主职责及其父级 owner。

移动源码归属时，应把路径和 import 调整与行为重构区分开。一个变更确实同时拥有两者时，可以
一起实施，但必须分别说明所有权变化和语义变化，并使用相应证据验证。

验收标准：从目录层级可以恢复模块的父子与同级关系，从文件名可以恢复模块内具体职责；局部改动
只要求理解受影响模块，新增入口或包装层必须拥有独立契约。

## 9. 依赖与外部工具

新增依赖前必须确认用途、替代方案、维护成本、许可证风险和跨平台影响。能用标准库或已有依赖清楚解决的问题，不得新增依赖。

外部工具适配必须隔离在拥有该工具调用的边界内：

1. 区分工具不可用、合法空结果和调用失败；已开始的调用失败不得伪装成成功空结果。
2. 保存必要的原始输出或摘要，便于复现解析问题。
3. 把外部工具版本、命令和退出状态纳入可观察结果。
4. 不得让外部工具的 stdout/stderr 直接成为稳定机器输出。

验收标准：依赖和外部工具失败不会破坏核心模型，也不会让调用方误判质量状态。

## 10. 稳定规则只引用 owner

稳定规则必须由对应 owner 完整表达。代码和验证脚本负责实现或校验规则，示例负责证明语义和
字段形状；这些消费材料只引用 owner，不建立第二规则来源。

当实现发现规则缺失、冲突或过期时，必须先判断 owner：

1. 行为、失败语义和输出责任回到[文档导航](navigation.md)指向的行为 owner。
2. 稳定序列化字段和兼容边界回到对应 schema 或协议 owner。
3. 测试层级、fixture 和验证入口回到测试策略 owner。
4. 目录、入口、依赖方向和组件责任回到架构或工具链 owner。

验收标准：任何稳定规则变化，都能指出唯一 owner，并说明本次改动同步了哪些受影响材料。

## 11. 验证按风险选择层级

验证范围随风险和影响面扩展。窄改动用局部测试验证不变量；跨边界改动覆盖调用链、输出层和错误映射；契约改动覆盖对应主规范、schema、示例和语义校验。

触及对应范围时，最低要求：

1. 内部语义有单元测试或等价局部验证。
2. 公共入口或跨组件集成边界有集成测试或等价入口验证。
3. 触及 owner schema 或示例时保持二者可互相映射，并运行既有 runtime validation 和契约测试。
4. 输出层边界和 stderr/stdout 边界有测试或脚本检查。
5. 纯文档改动至少用 `bun run validate -- docs`、局部 diff、关键词搜索或等价方式确认结构和范围。
6. 无法运行的验证必须在交付说明中明确原因和风险。

实现代码变更还应按影响面运行当前工具链提供的 dependency boundary、typecheck、lint 和 test。
只调整源码归属或路径的变更必须用迁移前后同一输入的行为对照，证明没有引入未声明的语义变化。

验收标准：验证能证明本次改动影响的边界仍成立，而不是只证明代码可以编译。

## 12. 变更前后自检与验收

自检只覆盖新增或修改代码及其直接受影响范围，不要求为没有问题的条目逐项留下记录。实现前确认
owner、实现归属、受影响边界和验证方式；提交或交付前检查：

1. 职责边界是否仍符合主规范。
2. 边界失败是否显式反馈，没有静默兜底。
3. 公开 API 是否通过类型或返回值表达不变量和失败。
4. 跨边界数据的责任方是否清晰。
5. 主导问题形态与实现模型是否匹配，并兑现该模型应有的数据流、不变量或失败可见性。
6. 控制流、集合处理、mutation、异步、参数、命名、注释和抽象是否满足局部可推理的硬下限；
   审查触发信号是否已定位到具体语义障碍，而不是被当成自动重构要求。
7. 涉及文件布局变化时，目录是否表达父子与同级模块关系，文件名是否表达模块内职责，且没有
   新增无 owner 的包装层或默认入口。
8. 稳定规则是否只有一个 owner；涉及 contract surface 时，是否同步规范、schema、示例、代码和验证。
9. 验证命令是否按改动范围运行并记录结果。

按[审查结论](#13-审查结论)交付发现：验收要求所有阻断性规则已经满足或具有有效例外；审查
触发信号关联到具体语义障碍后才形成整改要求；推荐路径的差异在仍然兑现相同语义价值时可以
保留。
