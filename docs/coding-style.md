# 编码规范

本文档定义 Vibe Check 实现代码的长期编码原则。它约束工程判断、实现模型、局部表达风格、
边界处理、职责分层和验收标准，不替代产品规范，也不预设具体模块名、函数名或重构方案。

具体 CLI 行为、输出字段、schema 形状、质量指标和测试矩阵，以
[文档导航](navigation.md) 指向的行为 owner 为准。本文只规定实现这些契约时的通用代码
性质、模型选择、表达边界和验证要求。

## 实现方向

产品实现的唯一 runtime owner 是 `src/product/**` 下的仓库自有 TypeScript/Bun 源码；
`scripts/**` 只保留开发自动化、CI consumer 和指向产品入口的薄 wrapper。产品源码不得
反向导入 `scripts/**` 或 toolkit gitlink。

正式集成入口是项目拥有的 Project Run。`scripts/quality/scan.ts` 只调用仓库 Project Run；Product CLI 仅提供 legacy migration diagnostic。已退役的 Rust 产品源码、测试、fixture 和模块结构不是当前
TypeScript 产品的实现来源或兼容层。

## 1. 文档边界与使用方式

编码规范只负责通用实现质量规则：如何识别 owner、如何处理边界、如何用类型表达领域含义、
如何按问题形态选择实现模型、如何保持局部代码可推理、如何组织模块、如何选择验证层级，
以及交付前检查什么。

按以下顺序读取和使用规则：

1. 先读取文档导航指向的行为 owner，确认稳定契约和实现归属。
2. 再使用本文选择实现模型、局部表达和验证层级。
3. 最后使用 TypeScript、ESLint 和相邻代码恢复可机械检查的限制与局部排版。

行为 owner 与本文冲突时，行为 owner 优先；工具配置执行可机械检查的语法、类型安全和
import 规则，不在本文逐项复制。相邻代码只提供局部上下文，不覆盖行为 owner 或本文规则。

验收标准：reviewer 能从改动说明或代码位置看出规则 owner、实现归属、影响边界和验证方式。

## 2. Owner 与实现归属先行

实现代码必须服从主规范定义的职责边界和稳定契约。owner 是规则来源文档；实现归属是承载代码的 source area、模块、文件或脚本。

新增逻辑先进入最明确的现有实现归属。只有职责、变化原因、复用边界或命名空间清晰时，才新增模块、package 或共享层。

优先在稳定 owner 中完成可维护实现。确需临时处理时，必须在相邻代码或 TODO 中写明适用范围和
移除条件；不得为短期跑通建立难以移除的第二套长期实现。

跨实现归属协作必须通过显式类型、稳定输出或主规范定义的边界完成。调用入口只做本入口负责的解析、校验、归一化和映射；属于下游组件的 opaque 值或业务语义原样传递。

共享代码不能用来绕过实现归属。只有多个实现归属共享同一不变量、错误映射或数据结构，且该共享职责有清晰命名和验证入口时，才抽出公共模块。

验收标准：新增或修改的代码能回答“谁定义规则、谁实现规则、谁消费结果、谁负责失败反馈”。

## 3. 边界代码显式

用户输入、CLI 参数、配置、路径、文件系统、进程、JSON、schema 和 scanner 输出都属于边界。边界代码负责解析、校验、归一化和错误映射；内部逻辑只处理已经归一化的领域对象。

边界失败必须给调用方明确反馈：

1. CLI 返回稳定退出码、清晰错误或可行动诊断。
2. 验证脚本说明文件、字段、命令和原因。
3. 机器输出、stderr/stdout 和人读报告保持各自通道职责。

不要用空结果、猜测默认值、静默跳过或隐式降级掩盖失败。可恢复兜底必须能追溯到主规范定义的输出层规则，并保留足够定位依据。

验收标准：任何失败路径都能回答“调用方下一步该看什么、改什么或重试什么”。

## 4. 类型表达领域含义

跨模块传递领域含义时，优先使用能表达不变量的 TypeScript 类型、discriminated union 和
只读数据结构。裸字符串、通用 JSON 值和 tuple 只适合协议镜像、opaque options、错误
details、测试构造和局部 glue code；外部输入先以 `unknown` 接收并在边界完成校验，不用
`any` 绕过边界。

类型设计遵循三条原则：

1. 业务逻辑入口接收已经校验过的领域值，不重复解析原始输入。
2. 稳定序列化类型保持字段形状清晰，不把私有语义塞进共享输出。
3. 公开 API 通过返回值、显式 result union 或可识别的 error 表达普通失败，不把缺失工具、解析失败或非法输入伪装成成功空结果。

稳定字段、错误码、退出码、schema 名、诊断前缀和跨函数复用的字符串或数字，应使用枚举、新类型、常量模块或职责内配置表达。不要建立跨组件的全局杂物常量池。

验收标准：阅读函数签名时，可以区分“原始输入”“领域对象”“输出模型”和“私有参数”。

## 5. 按问题形态选择实现模型

按以下顺序选择实现模型：

1. 行为 owner 或组件契约已经规定模型时，使用该模型。
2. 没有更具体约定时，识别当前职责的主导问题形态。
3. 从下表选择能直接呈现不变量、数据流和失败路径的模型。
4. 只有模型需要且触发条件成立时，才使用预置能力。
5. 用测试或等价证据验证表中声明的实现价值。

一个流程可以在明确的职责边界内组合多种模型，但同一职责应保持稳定表达。

| 主导问题形态 | 优先实现模型 | 实现必须呈现的价值 |
| --- | --- | --- |
| 无状态计算或数据转换 | 纯函数与显式组合 | 输入输出直接，计算可独立验证，不依赖隐藏状态 |
| 有明确顺序、副作用和失败恢复的工作流 | 结构化过程或事务式流程 | 执行顺序、提交点和失败路径连续可见 |
| 有稳定身份、生命周期或持续不变量 | 对象或 class 封装 | 状态和行为由同一责任边界维护，非法状态不向外泄漏 |
| 取值与分支集合封闭，结果只取决于当前值 | 判别联合与穷尽分支 | 合法取值和处理完整显式，新增分支能够被整体检查 |
| 行为同时取决于当前状态和事件，合法转移受约束 | 显式状态转移模型 | 状态、事件、guard 和合法转移能够分别识别 |
| 调用契约稳定，但行为需要独立替换或扩展 | 接口、策略对象或多态 | 差异集中在实现侧，调用方不重复选择规则 |
| 存在大量同构规则、字段或映射 | Schema、表驱动或声明式定义 | 规则集中且结构一致，扩展主要修改定义而非复制控制流 |
| 数据经过多个职责稳定的连续阶段 | 流水线 | 阶段输入输出和组合顺序清楚，各阶段可单独验证 |
| 独立参与方围绕事件和时序协作 | 事件或消息驱动 | 事件契约、订阅者责任和时序影响显式 |
| 数据关系、访问模式或批处理成本主导实现 | 数据导向设计 | 数据布局贴合真实工作负载，复杂度取舍有测量依据 |

预置能力只解决下表列出的语义，不构成迁移要求：

| 能力 | 使用条件 | 使用边界 |
| --- | --- | --- |
| `TypeBox` | 行为 owner 需要 runtime Schema、外部数据解析和静态类型派生 | 复用已有 Schema owner，不建立同义 Schema |
| 项目自有 [`Option`](../src/product/foundation/src/option.ts) | 值可能存在或缺失，并且缺失本身不是失败 | nullable 边界使用 `fromNullable`；缺失需要失败原因时使用 `toResult` 转为 `neverthrow.Result` |
| `neverthrow` | 可预期失败需要跨多个步骤或异步流程组合 | 简单局部边界继续使用已有 typed error 或显式 result union；同一边界只使用一种失败协议 |
| `ts-pattern` | 封闭分支包含非平凡的判别联合、嵌套结构或表达式结果，并需要穷尽检查 | 简单单值分支使用原生 `switch` 与 `never`；它不承接状态机生命周期 |
| `Remeda` | 连续无状态数据转换是当前职责的主要结构 | 简单数组操作使用原生方法；复杂分支、副作用或 `await` 使用结构化循环 |
| `Mnemonist` | 访问模式、复杂度或专用语义明确需要 Heap、Deque、Trie、LRU 等结构 | 普通集合使用原生 `Array`、`Map` 与 `Set` |

选型依据与复核边界见
[Result/Option](investigations/implementation-libraries/result-and-option-libraries.md)、
[穷尽匹配/状态建模](investigations/implementation-libraries/pattern-matching-and-state-modeling-libraries.md)
和[函数式工具/数据结构](investigations/implementation-libraries/functional-utilities-and-data-structures.md)
调查。没有表中触发条件时，使用能完整表达当前职责的最简单语言结构。现有能力不能覆盖真实
问题时，把缺口交给依赖 owner 重新评估；实现任务不临时安装同类替代库，也不建立第二套基础原语。

验收标准：实现者能说明主导问题形态、所选模型及其兑现的价值；reviewer 无需从语法偏好猜测
状态、顺序、扩展点或失败语义。

## 6. 局部表达保持可推理

代码应让主要数据流和成功路径能够自上而下阅读。小型入口可以组合多个职责；一旦解析、领域
判断、副作用、输出或错误映射开始互相遮蔽，就用有领域名称的中间值或函数恢复边界，而不是
继续压缩表达式。

| 关注点 | 默认表达 | 重构触发信号 |
| --- | --- | --- |
| 控制流 | 前置条件和失败使用 guard clause，主要成功路径保持连续 | 嵌套分支迫使读者同时记住多个条件，或提前返回把一个简单决策切碎 |
| 条件表达 | 三元表达式只用于一个清楚的二值选择；封闭集合使用穷尽分支 | 嵌套三元表达式；同一复合条件重复出现；条件同时决定多个互不相关的行为 |
| 集合处理 | 直接无状态转换使用 `map`、`filter`、`flatMap`；含 `await`、短路、分支副作用或有状态累计时使用结构化循环 | 用 `reduce` 隐藏多步工作流或可变累计器；用异步 `forEach` 制造未观察 Promise；长链中混入分支与副作用 |
| 状态与 mutation | 默认使用 `const` 和只读输入；局部 mutation 只在 owner、生命周期和提交点一眼可见时使用 | 修改调用方传入对象；跨模块共享可变状态；通过闭包或 module global 隐藏一次调用的状态 |
| 异步与并发 | 有依赖的步骤顺序 `await`；相互独立且规模有界的工作才并发；需要限流时使用已有调度边界 | 漂浮 Promise；为缩短耗时盲目 `Promise.all`；把本应独立的工作意外串行化；在循环中隐藏无界并发 |
| 函数与参数 | 函数围绕一个可命名结果；多个同类型或可选参数使用具名 options；helper 承接真实领域步骤或独立证明责任 | 用布尔 flag 切换互不相关流程；只转发参数的 wrapper；仅按行数拆函数；用位置参数迫使调用方记忆含义 |
| 命名 | 使用领域名词和明确动作或结果；布尔值使用 `is`、`has`、`can`、`should` 等可判读前缀；路径、单位和时间基准写入名称 | 在跨函数或跨模块契约中使用裸 `data`、`item`、`value`、`result`、`handle` 等无法区分责任的名称 |
| 注释 | 解释取舍、不变量、边界责任、非显然约束和必须保留的原因 | 复述语法或控制流；用注释代替可命名结构；没有适用范围和移除条件的长期 TODO |
| 抽象 | 选择直接兑现当前模型价值的最小结构；共享抽象必须有稳定不变量、owner 和消费方 | 把 class 当命名空间；为单一局部实现预设接口；因假设复用建立 generic helper；用新抽象包住已有抽象而不增加契约 |

链式表达只有在每一步仍能用领域语言识别时才保持内联；回调需要多层分支、mutation、错误映射
或副作用时，改用具名阶段或结构化循环。偏离本节默认表达必须来自更具体的行为 owner、公共
兼容性、经过测量的性能约束或现有组件契约，并让理由和验证证据在相邻代码或测试中可见；
“附近代码也这样写”本身不是偏离依据。

验收标准：reviewer 可以沿单一局部路径恢复输入如何成为结果、状态在哪里改变、异步工作何时
完成，以及每个抽象解决了什么当前问题。

## 7. 错误处理与结果模型

错误类型按边界和调用方需求设计。内部 helper 可以返回具体错误；跨模块和 CLI 边界应映射为稳定、可解释、可测试的错误模型。

错误处理规则：

1. 可预期失败使用显式 result union、受控 exception 或调用链已有的 typed error；不要混用多种失败协议描述同一边界。
2. Promise 必须被 `await`、返回或显式处理；生产路径不得遗留未观察 rejection。
3. 外部命令失败、工具不可用、解析失败和无发现分别建模。
4. `catch` 中把未知值按 `unknown` 处理，并在统一边界生成可定位、可行动的消息。

验收标准：错误路径能被测试或命令输出观察到，并且不会把不同失败混成同一种状态。

## 8. 文件与模块按变化原因组织

文件、模块、函数和脚本应围绕单一变化原因组织。编码规范不规定固定目录方案；具体拆分服从当前代码形状和相邻模块惯例。

新增代码先进入最明确的现有实现归属。把现有 runtime 源码移动到新的 owner 时，应保持
已有文件分组、类型和控制流，只做路径、import、入口和所有权所需调整；不借搬移新增
领域层、adapter 层或 service 层。

TypeScript 模块使用显式相对 import 和清晰 source entrypoint。产品 runtime 闭包必须位于
`src/product/**`；仍属于仓库开发自动化的 consumer 留在 `scripts/**`，只允许
`scripts/** -> src/product/**` 的单向依赖。

需要拆分的信号：

1. 同一文件同时承载多个组件职责、多个输出边界或多个边界类型。
2. 新功能需要反复修改无关代码。
3. 测试、fixture、解析、输出和错误映射互相遮蔽。
4. reviewer 无法用一句话说明该单元的主职责。

验收标准：文件路径和文件名能表达实现归属；局部改动不会迫使读者理解无关组件或无关输出边界。

## 9. 依赖与外部工具

新增依赖前确认用途、替代方案、维护成本、许可证风险和跨平台影响。能用标准库或已有依赖清楚解决的问题，不新增依赖。

外部工具适配要隔离在 scanner 或 tooling 边界内：

1. 检测并报告工具可用性；保持现有 preflight skip 与 no-finding 可区分，已进入 invocation
   后的失败不得伪装成扫描通过。
2. 保存必要的原始输出或摘要，便于复现解析问题。
3. 把外部工具版本、命令和退出状态纳入可观察结果。
4. 不让外部工具的 stdout/stderr 直接成为稳定机器输出。

验收标准：依赖和外部工具失败不会破坏核心模型，也不会让调用方误判质量状态。

## 10. 稳定规则只引用 owner

代码和验证脚本用于实现或校验规则，不成为新的规则来源。示例用于证明语义和字段形状，不替代主规范或 schema。

当实现发现规则缺失、冲突或过期时，先判断 owner：

1. Project Definition、Run Controls、project root、console 和 structured result 由 Configuration / Output owner 定义；项目自有 command adapter 才拥有自己的进程状态映射。
2. 指标模型、warning 语义和报告数据由 Core / Scanner owner 定义。
3. 已有 owner schema 的稳定 JSON 字段由 schema 定义；当前 TypeScript quality artifacts
   使用产品 runtime validation，不套用已退役的 Rust report schema。
4. 测试层级、fixture 和验证入口由测试策略定义。

验收标准：任何稳定规则变化，都能指出唯一 owner，并说明本次改动同步了哪些受影响材料。

## 11. 验证按风险选择层级

验证范围随风险和影响面扩展。窄改动用局部测试验证不变量；跨边界改动覆盖调用链、输出层和错误映射；契约改动覆盖对应主规范、schema、示例和语义校验。

触及对应范围时，最低要求：

1. 内部语义有单元测试或等价局部验证。
2. Package Run 或 retained CLI migration diagnostic 有集成测试或等价入口验证。
3. 触及 owner schema/examples 时保持二者可互相映射；TypeScript machine artifacts 运行
   既有 runtime validation 和相应契约测试。
4. 输出层边界和 stderr/stdout 边界有测试或脚本检查。
5. 纯文档改动至少用 `bun run validate:docs`、局部 diff、关键词搜索或等价方式确认结构和范围。
6. 无法运行的验证必须在交付说明中明确原因和风险。

TypeScript 产品变更还应按影响面运行 product import boundary、typecheck、lint 和 test。
源码归位类 change 必须用迁移前后同一输入的行为对照证明路径调整没有改变既有参数、
scanner、warning、baseline、artifact 或状态语义。

验收标准：验证能证明本次改动影响的边界仍成立，而不是只证明代码可以编译。

## 12. 变更前后自检

实现前确认 owner、实现归属、受影响边界和验证方式；提交或交付前检查：

1. 职责边界是否仍符合主规范。
2. 边界失败是否显式反馈，没有静默兜底。
3. 公开 API 是否通过类型或返回值表达不变量和失败。
4. 跨边界数据的责任方是否清晰。
5. 主导问题形态与实现模型是否匹配，并兑现该模型应有的数据流、不变量或失败可见性。
