# 从项目质量目标构建 Gate

项目 Gate 在约定的输入和环境下收集质量证据，给出可解释的放行决定，并让开发者及时得到反馈。本文以一个有配置、测试和构建产物的项目为例，依次设计判决、执行关系和日常入口，最后根据实测成本演进。示例中的目标和阈值是项目选择，不是 Vibe Check 的默认要求。

Vibe Check 提供程序化 API，不提供现成 CLI；项目拥有 Definition、入口及其放行策略。精确 API 契约由链接的随包专题定义。

## 从质量目标到可判定的证据

先写下项目要阻止什么，再决定怎样取得证据。假设发布前需要以下结论：

| 质量目标 | 证据及失败含义 | 放行决定 |
| --- | --- | --- |
| 配置可读取 | 正式配置文件均为合法 JSON；语法错误意味着配置不能可靠读取。 | 阻断；无匹配文件也不能证明目标成立。 |
| 项目行为正确 | 项目测试在指定运行时及依赖下通过；断言失败意味着已知行为不满足。 | 阻断；测试无法启动也不能视作通过。 |
| 产物可运行 | 同一次构建出的包在干净环境中安装并通过运行验收；失败说明交付物不可用。 | 阻断。 |
| 产物大小受控 | 测量同一包的大小并与项目预算比较；超出预算不代表它不可运行。 | 本例阻断；项目也可明确将其作为提醒。 |

这张表是设计的起点：写明输入、环境、通过条件、无法获得证据时怎么办，以及谁使用结果。JSON 语法检查只证明文件可解析；如果字段或跨文件关系重要，应增加对应的 schema 或业务验收。

提醒与阻断要体现在结果策略中；warning message 本身不会改变 Check 状态。支持 `findingPolicy` 的随包 Check 可设置阻断或非阻断，工具不可用时仍为 `unavailable`，不能视为通过。

### 按独立结论划分 Check

测试失败、产物不能运行和大小超标分别告诉维护者不同的事情，值得分别判断。构建、打包、读取大小如果只服务一个大小结论，可以作为同一 Check 的步骤；当运行验收也要用同一包时，再把准备材料作为共享节点。这样既保留各项失败的含义，也使准备步骤服务于实际的验收目的。

### 选择证据的取得方式

根据项目已有能力选择接法：

- 已有适用规则：配置[随包 Check](../../README.md#随包提供的-check)，例如 JSON 语法检查。
- 已有稳定的命令和退出码：用 [`commandCheck`](command-check.md#接入项目已有命令) 保留其领域逻辑，区分质量失败与启动失败、超时等不可用状态。
- 已有可 import 且无 CLI 副作用的函数：在自定义 Check 中直接调用并映射领域结果；仍须承担取消、清理和隔离责任。
- 项目独有规则：从 [README 自定义 Check](../../README.md#自定义-check-快速开始)定义输入、判决和数据，再按[扩展指南](extending-check-lifecycle.md)补齐需要的生命周期。

选择直接函数还是命令取决于所需边界。函数可能省掉启动和序列化，但不提供独立进程隔离或强制终止；会自动启动 CLI、调用 `process.exit` 或修改全局环境的模块不能当作普通函数 import。

命令用 executable 和独立 arguments 表达，按需显式提供环境、timeout 与输出限额；不要依赖隐式 shell 或默认继承环境。工具输出需要位置诊断时，按[命令诊断](command-check.md#将工具结果映射为诊断)验证协议、映射 Records，并在发布前处理敏感信息。

## 设计执行图与材料生命周期

从上表得到的运行关系可以是：

```text
配置检查 ────────────────┐
测试 ────────────────────┤
准备包 ─┬─> 大小验收 ────┤──> Gate 放行决定
        └─> 安装/运行验收 ┘
```

### 共享准备，分别判决

准备包证明材料已准备好；两个消费者各自给出判决。两者应指向**同一次构建的身份和位置**，例如构建版本、路径或摘要，而不是各自寻找一个叫 `dist` 的目录。大小失败时运行验收仍可独立进行；准备失败则没有可验收材料，两个消费者都不能报告通过。[共享准备示例](check-dependencies.md#共享准备与独立判决示例)用固定清单演示一次准备、两条独立判决与失败阻断；真实项目需替换为自己的构建和验收。

### 表达依赖与观察

在 Definition 中用 `dependsOn` 表达需要上游**成功**的直接依赖；需要在失败后仍汇总结果的审计则用 `observes` 等待**终态**。观察者自身通过不改变上游失败或总判决；两种关系只授权读取直接声明的节点，观察也不会自动选择被观察者。对比可运行的[终态观察示例](check-dependencies.md#成功依赖与终态观察示例)。

### 管理材料与隔离

共享只适用于可安全共享的事实和材料。准备 owner 应明确材料身份、位置、可写者和最后消费者；临时目录可在 Run 外层用 `try/finally`，待所有消费者结束或取消后清理。

破坏性测试、独立失败注入、不同运行时或冷安装验收可能需要隔离副本或独立准备，避免消费者互相污染证据。传递普通摘要和路径时优先使用 canonical data；确需同一 Run 的非 JSON 引用时再考虑 handoff，规则见[依赖与类型化数据](check-dependencies.md)。

### 简化执行路径

检查工作可以在一个 Check 内调用多个步骤；也可以由已有命令完成整个工作流。沿调用链移除只转发且无独立责任的包装可减少复杂性，但不能移除必要的环境、超时、取消、输出和隔离边界。先确认什么结论及资源责任会因此改变，再缩短路径。

## 建立项目入口

先将第一项配置证据接成真实可运行的 Gate，再按上面的设计逐项加入测试与产物验收。本例检查 `config/**/*.json` 的语法：合法输入退出 `0`，无效或未完成的检查退出非零。字段与结构约束可用 [JSON Schema 检查](../checks/json-schema-validation.md)覆盖。

### 准备项目与输入

使用 [README 声明的 Node 运行环境](../../README.md#安装)（Node `>=24.18`）。下面统一用 pnpm 管理项目依赖和脚本；也可使用项目已有的 package manager。进入你要检查的项目根目录，安装依赖：

```sh
pnpm add -D @zxyycom/vibe-check
```

在该根目录创建 `config/app.json`：

```json
{"name":"demo"}
```

本例需要的文件关系是：

```text
my-project/
  package.json
  pnpm-lock.yaml
  quality.ts
  config/
    app.json
```

### 编写完整入口

本例按 ESM 编写。在同一项目根目录创建 `quality.ts`；若已有 CommonJS 项目明确声明了 `"type": "commonjs"`，改用 `quality.mts` 并同步下文命令与 script，不必切换整个项目的模块语义：

```ts
import { defineConfig, jsonValidation, run } from "@zxyycom/vibe-check";

const definition = defineConfig({
  checks: [
    jsonValidation({
      checkId: "config-json",
      files: { patterns: ["config/**/*.json"] }
    })
  ],
  outputs: { machinePublication: { enabled: false } }
});

async function runGate(projectRoot = process.cwd()) {
  const result = await run(definition, { projectRoot });
  process.exitCode = result.kind === "completed" && result.aggregate === "passed" ? 0 : 1;
  return result;
}

if (import.meta.main) await runGate();
```

`import.meta.main` 让脚本在直接执行时调用项目函数 `runGate`，被 import 时保持不启动。`projectRoot` 默认取调用时的工作目录，文件选择都相对于它。

下文命令在项目根目录运行。从其它目录启动时，把末行调用改为 `runGate("/absolute/path/to/my-project")`；对应的 API 控制是 `run(definition, { projectRoot })`。

### 先验证通过与失败

执行入口：

```sh
node quality.ts
```

依次核对三种结果：

1. 当前合法输入：`config-json` 通过，进程退出 `0`。
2. 将 `config/app.json` 临时改为 `{"name": }`：检查失败，进程退出 `1`。
3. 修复输入：重新通过。POSIX shell 可紧接命令执行 `echo $?` 查看退出码。

终端保留默认进度和结果预览；本例关闭 machine publication，不生成 `run.json` 或 `records.ndjson`，diagnostic logging 也保持默认关闭。无效 JSON 形成带相对路径与原因的 Record，这里是 `config/app.json / invalid-json`。数据结构见 [JSON 检查](../checks/json-validation.md)，机器文件配置见[输出指南](run-outputs.md)。

退出码由项目入口决定：

- `completed` 只表示 Run 已完整结算，仍要检查 `aggregate === "passed"`。
- 默认聚合要求有效 Check 列表非空且每项都 `passed`。本例没有匹配文件时，Check 是 `not-applicable`，因此也退出 `1`，不会把错目录或空输入当成成功。
- `failed`、`unavailable`、取消和其它非 `completed` 返回分支均不能放行；输出失败的 `output` 分支即使 aggregate 通过也不放行。未捕获的调用异常会令 Node 非零退出，不应在外层吞掉异常再报告成功。

### 固定本地与 CI 的同一入口

将以下字段合并进项目已有的 `package.json`，保留其它依赖和 scripts：

```json
{
  "scripts": {
    "quality": "node quality.ts"
  }
}
```

本地统一执行 `pnpm run quality`。把输入、入口、package script 和 lockfile 纳入项目版本管理。CI 准备相同的 Node 与 pnpm 环境、取得这些文件后，在项目根目录依次执行：

```sh
pnpm install --frozen-lockfile
pnpm run quality
```

CI 需要安装这个开发依赖，并以安装和检查步骤的退出码判定成败；`|| true` 等吞掉非零退出的处理会破坏这条接线。

完成这些对照后，第一项检查已有可用入口；再按前面的执行图加入项目实际需要的测试与产物验收。

### 运行专题片段

专题中的 Definition 片段展示局部设计。按专题准备输入并保存到项目根目录：只含 `definition` 的片段需要补 `run` 导入，并追加[完整入口](#编写完整入口)中的 `runGate` 与直接执行判断；已有 `runGate` 和直接执行判断的片段使用自己的入口。

执行 `node quality.ts`，对照专题的 Check outcome、aggregate 和退出码。固定数据和短等待用于演示关系，接入项目时应替换为真实工作。

## 按实际成本演进，保留证明能力

### 先测量，再选择措施

固定输入、源码和产物身份、工具版本、机器资源与并发条件，测量入口到退出的端到端时间，并区分安装、构建、测试、进程和输出等阶段。冷、热缓存分开重复测量，入口之前发生的准备也计入总成本。

执行图中的共享准备和精简包装可以减少重复工作；用测量确认它们是否真正降低总成本。每次改变一个主要因素，在相同条件下复测耗时、资源峰值及成功/失败对照，再结合收益、波动和维护成本决定是否保留。

### 缩小执行范围

本地快速任务和 CI 完整任务可共用入口，以经过验证的任务名映射 flags。拒绝未知任务，确保选中下游时所需前置项也被选择，并明确未选检查不属于本次证明范围。[任务选择示例](extending-check-lifecycle.md#按任务选择检查示例)展示这种映射；完整入口应保留明确的全量路径。

无关改动仍触发大量工作时，可进一步根据真实输入选择检查。region 需要覆盖源码、测试、fixture、共享工具、配置及生成器等实际输入；新增、删除和共享输入都应触发，未知依赖走保守路径。

例如共享 JSON reader 改动可能同时触发 configuration 测试；全源 identity 审计仍需覆盖整棵源码树。链接检查可能受目标文件删除影响；未建模反向依赖时保留完整检查。`HEAD` 比较适合未提交工作区，PR 应采用项目取得的正确基准；Git 证据不可用与可信的零命中不同，须设计保守回退。见[按文件变化选择示例](selecting-checks-by-git-changes.md#按真实输入增量选择示例)。

### 复用计算与约束竞争

同样输入反复计算昂贵事实时，可以缓存测量结果，并在每次运行时按当前规则判决。key 要覆盖影响计算的内容、版本和参数；校验 payload，并验证失效、损坏和计算失败路径。[缓存测量示例](cache-results.md#缓存测量而非判决示例)展示如何复用大小而非通过结论。

并行任务争抢资源或修改同一材料时，对稀缺资源设置容量，对冲突写入设置互斥，并保留必要隔离。配额是逻辑约束；比较不同并发下的耗时和峰值，判断适合项目的设置。见[并发约束示例](scheduling.md#并发约束示例)。

## 验收项目 Gate

用项目自身输入和失败注入回答以下问题：

1. 每个质量目标由哪些证据证明？无输入、工具不可用、取消或输出失败时为什么不会误放行？哪些失败是提醒，哪些阻断？
2. 每个 Check 的失败能说明什么？共享准备、消费者与观察者是否各有独立责任，准备失败和单个消费者失败是否得到预期结果？
3. 消费者是否读取同一正确材料，隔离、所有权和最后消费者后的清理是否成立？函数与命令的取消、环境与隔离边界是否符合实际？
4. 本地与 CI 是否运行同一入口，并使用明确的根目录、环境和退出规则？选定任务后哪些结论不在本次证明范围内？
5. 若使用增量、缓存或并发，相关输入变化、跳过、失效、冲突和完整运行的对照是否覆盖？同条件复测后，原有失败注入与独立证明是否仍成立？
